# 书稿一致性审查

目标：让送审的章节本身经得起审核——同一对象的完整名称及对应表述一致；不以“意思差不多”放过多字、少字、换字，也不把不同概念机械统一。

**名词表的首要作用是把本章的一致性问题找全**。送审一般是文前加 1～2 章，每一章都要经得起审核。所以每章先逐段精读，把本章所有命名对象和它们的全部写法读出来建成本章名词表，再拿它查本章。名词表同时继续往下传：每章审完，把会在后面章节再出现的对象并入总名词表（起点是书名、前言、目录），后面的章节据此做跨章核对。往下传是附带的，不能用传下来的表代替本章的逐段精读。

**分工**：一个会话审一本书。主代理负责准备、建总名词表、派单、收活、问用户、写入和汇报；每章由一个章子代理在干净上下文中审读，再由一个复核子代理重判放过清单。本文件只写主代理的活，子代理的规则在 references 里，各读各的：

| 谁 | 读什么 |
|---|---|
| 主代理 | 本文件、[判定规则与改法写法](references/rules.md)、知识库主表；做到对应步骤时读 [工作文件模板](references/templates.md)、[派单模板](references/chapter-subagent-prompt.md) |
| 章子代理 | rules.md、[章子代理核查细则](references/chapter-checks.md)、templates.md、知识库主表；有图表时加 [图表内容核对](references/figure-table-content.md) |
| 复核子代理 | rules.md、知识库主表 |

- **子代理不读本文件**，也看不到主代理的对话：用 Agent 工具的 `general-purpose` 类型新开，不用 `fork`（fork 会把主会话整段带进去）。它要知道的本书情况（用户已定的方向、D 项、机械替换、重点防范）都由主代理写进派单。
- 主代理不读 chapter-checks.md；收活时只读摘要和脚本输出，抽查记录文件，不把整章内容拉回自己的上下文。

## 一、范围

**审查内容**
- 名称与术语：同一对象的中文名、英文名、缩写、公式中的指标符号、图内标签、表格项。
- 核心命题：书名、前言、目录、导语、章节标题中的核心说法。
- 总述与分述：学习目标表、模块表、“本节将从……方面”“分别介绍”、章末回顾与后文的逐项对应。
- 图表与正文：名称、数量分类、层级流程、数据结论、覆盖冗余（细则见 [图表内容核对](references/figure-table-content.md)）。
- 案例内部：同一案例的背景、表现、原因、方案、启示之间的称谓及作者自拟核心判断。
- 跨章回指：“第×章介绍/定义的……”定向核对原章。
- 习题与答案、小结与正文的对应。

**不在范围内**：公式推导与数学符号正斜体、图表编号与首次引用顺序、搭配润色（如“防范……风险”属搭配补全，另行归类）、专业事实正确性。用户限定只查某一维度时按限定缩小范围。

## 二、工作文件

在用户指定位置（默认当前工作目录）建立 `<书名>-一致性审查/`：

```
<书名>-一致性审查/
├── source/               # 分章提取的文字（带页码标记）、脚本候选（第NN章-候选.md、第NN章-变体候选.md）及必要的页面图
├── 名词表.md              # 总名词表：从书名、前言、目录建起，每章审完并入跨章对象，往下传
├── 待定决策.md            # 有倾向的建议（D-xx）：倾向方案、另一个选项、涉及章节、状态
├── 第01章-名词表.md        # 本章所有命名对象及其全部写法，用来查本章问题
├── 第01章-审查记录.md      # 本章问题表 + 覆盖记录
├── 第01章-修订规则.json    # 子代理写的修订和批注，由主代理写入副本
├── 第01章-机械规则.json    # 主代理自己处理的已定机械替换
├── 第01章-复核记录.md      # 压缩复核的结果，附 第01章-复核规则.json
├── 回查清单.md            # 跨章回指等需到其他章核对的项（可选）
├── ...
└── 一致性审查报告.html     # 全书汇总（用户要求时才出）
```

各文件格式见 [工作文件模板](references/templates.md)。

**Python 环境**：Claude 与 Codex 的书稿审校 skill 共用 `~/.venvs/book-review/`，所有脚本都用 `~/.venvs/book-review/bin/python` 运行，依赖见 `~/.venvs/book-review/requirements.txt`（锁定版本见同目录 `requirements.lock.txt`）。不要另装环境，也不要改用系统 Python 或其他项目的虚拟环境。环境损坏时按 requirements.txt 顶部的命令重建。

**辅助脚本**（`scripts/`，用 `~/.venvs/book-review/bin/python` 运行）：
- `dump_docx.py <docx>`：提取段落和表格，标出修订 `[+插入+]` `[-删除-]` 和批注范围，结果存入 `source/`。
- `hidden_text.py <docx>`：列出不可见的文字（白色、隐藏、极小字号），审读前排除。
- `term_candidates.py <段落文件> [图表文字.md] --search <必搜写法,…> [--heads <本书中心词,…>] -o <输出.md>`：按中心词（方法、模型、算法、指标、理论、制度、机构……）把词组分组列出，同一组里“监督分类模型／监督学习模型／无监督模型”摆在一起；另列英文缩写前后的称谓（“××算法——EC-TR”“该方法”）和必搜写法命中位置。是建本章名词表的候选草稿，噪音要人判。
- `variant_pairs.py <段落文件> [图表文字.txt] <输出.md>`：找出本章“只差一个字”的写法配对（换字、增删字、末字换字），逐对给结论。
- `check_glossary.py <第NN章-名词表.md>`：名词表门禁。列出有多种写法却没有结论的行（判断栏只写“一致／保留／描述性／同位语／叙述”而没写内容区别的），以及“非同一对象”表里没有原文位置的依据。子代理交活前跑到 0 条，主代理收到后再跑一遍。
- 通读技能的 `~/.claude/skills/tongdu/scripts/check_rules.py <原稿> <规则1.json> [规则2.json …] [--merge 合并规则.json]`：写入前预检。按写入顺序模拟，查 `ctx` 找不找得到、`old`／`target` 在不在该段、前后规则有没有互相踩到、同段有没有重复批注；错误为 0 才写入。`old` 跨不跨 run 都能写入，不用另查。
- `revise_docx.py <原稿> <输出> <规则.json>`：在副本上写入最小差异的真实修订和批注，原稿不动。写完自动调用 `comment_links.py`：批注里“x.x.x节“原文””“图x-x“原文””这类位置改成跳转链接（⌘+点击跳到并选中那句原文）；输出末尾列出没对上的，多是引文与正文不一字一致，改成原句后重跑。规则格式为 `{"edits":[{"ctx","old","new"}], "comments":[{"ctx","target","text"}]}`，其中 `ctx` 用于定位段落；错在脚注里的，edits、comments 加 `"part": "footnote"`，直接在脚注里改（check_rules 同样支持）。批注怎么写见 [rules.md](references/rules.md) 第三节。

## 三、流程

### 阶段 0：准备（主代理）

1. **读案例主表**：完整读取 `/Users/xiewentao/Desktop/一致性审读知识库/一致性审读知识库.md`。缺失或无法读取时告知用户并请求恢复，不以记忆冒充。用一两句话告诉用户本书重点防范的漏检类型。主表中的具体替换不是跨书词表。
2. **固定稿本与范围**：确认文件、审查章节、是否只查某一维度。稿子先做过润色（润色技能 `runse`）的，在**润色后底稿**上审，不用作者原稿；润色的 `复查汇总.md` 里“留给一致性审查的名词”当变体候选的线索，写进子代理派单。有修订或批注时分别识别修改前、修改后和批注要求，删除文字与插入文字不能拼成一条“现文”，批注未落实也要报。
3. **分章提取**：用共用环境 `~/.venvs/book-review/bin/python` 运行脚本（见上文“Python 环境”）。PDF 按页提取文字（可用 PyMuPDF，或参考 `anthropic-skills:pdf` 技能），每页加 `[p.N]` 标记；DOCX 用 `scripts/dump_docx.py` 提取（标出修订和批注）。按章存入 `source/`，并记下每章页码范围。DOCX 必须先运行 `scripts/hidden_text.py` 列出白色、隐藏、极小字号的文字，再对照排版后的 PDF 页面（或渲染页）判断是否可见：
- 下面没有底图的白字是模板占位（如丛书名、内容简介、CIP、定价），不可见，不算正文，也不能作为判断依据，不报问题、不加批注、不改；覆盖记录中注明“不可见占位文字，范围外”。
- 压在深色标题图上的白字（如章题、节号）是可见正文，照常审查。
- 没有 PDF 时把白字列为“可见性待确认”，不直接判断。

按章切分时，以**可见的章标题段落**（标题样式）作为起点。有的排版稿在章标题图下方另有一行白色的章题副本，切分起点不能落在副本上，否则会漏掉真正的章题，修订也会写到不可见的副本上。修订规则里的章题 `ctx` 要能定位到可见的那一段，写完后用 `dump_docx.py` 确认修订落在哪一段。

页眉页脚另行检查：如果是引用章标题的自动域（STYLEREF），改了章标题就会同步，不单独报。图片化文字、公式、自动编号提取异常时，需要回看原页（Read 工具的 `pages` 参数）。

4. **每章跑脚本候选**（派子代理前）：`term_candidates.py`（`--search` 填总名词表的必搜写法，`--heads` 填本书名词类别清单里的中心词）和 `variant_pairs.py`，结果存 `source/第NN章-候选.md`、`source/第NN章-变体候选.md`，写进派单作为建表的起点。
5. **已定的机械替换不交给子代理**：用户已确认、体例已定的整词替换（如“方案→方法”“GÉANT→Geant”、式号括号），主代理自己写成 `第NN章-机械规则.json` 用 `revise_docx.py` 处理，派单里只告诉子代理“这些已由主代理处理，不要再写”。子代理的注意力留给读和判断。

### 阶段 1：建立总名词表（主代理）

1. 读书名、前言（序言、导读）、目录，以及书中已有的术语表或缩略语表。
2. 为其中的核心对象建立条目：所指对象、采用名称、依据原文及位置、状态。目录中送审章节的各级标题逐条纳入，它们是审各章标题和正文的直接依据。
   - **书名中的核心名称最重要，列为第一条**：逐字登记，不加“（系统）”这类可省括注；把依次去掉各修饰词的缺字写法列为“必搜写法”，每章都搜一遍、逐处判断（指研究领域／任务时用完整名称，指对象本身时可用短称，两种用法在条目里写清楚）。书名核心词与前言、目录、正文里的近义写法（如“工厂供电／工厂供配电”），主代理**不许预判成“不同对象”或“不同用法”**，一律列进“待用户确认”，在第 6 步问用户定（2026-11-16 用户定：《工厂供电》一书主代理把两者判成“课程名／系统名”写进非同一对象表，子代理和复核照着放过，核心词没统一）。
   - **各章章题的核心名称也在一开始登记**，同样列出缺字写法。
   - 这些条目审读中发现有误，随时修改，已审章节按改后的条目回查补改。
3. 同时登记“非同一对象，不得合并”的对照组。
4. **定本书的名词类别清单**，写在总名词表开头“〇、本书名词类别清单”：从模板的通用底表（研究对象与核心命题、作者自己提出的东西、它的组成部分、类别与对比对象、专名、术语、数据与出处、结构性文字）出发，按书名、目录、第 1 章增删，每类写上本书的例子和中心词（理工书：方法、模型、算法、指标、数据集；文科书：人名、机构、作品与文献名、法规政策、事件与时期、学派、概念）。这张清单只是防整类漏收的检查单，不是收录范围——收录范围仍是本章出现的所有命名对象。
5. 总名词表起步时只收核心对象，以后每章审完再并入；把本章的对象收全是本章名词表的事。
6. 把总名词表、名词类别清单和其中的待确认项简要展示给用户；**影响统一方向的待确认项先问清楚再开始审章节**，等用户答复后才派子代理。至少要问：书名核心名称与正文近义写法统一成哪个、各章章题核心名称、前言／目录与正文写法冲突的对象。每项写清两种写法、各自出现次数和位置、倾向与依据，用选项让用户直接选。
   - **这一步必须停下来问**（2026-11-16 用户定：“以后还是要和我确定”）。开审之后本章的 D 项、体例待定项在阶段 2 第 4 步复核交回后再问一次。
   - 用户已定的写进总名词表，状态“用户确认”；子代理照此执行，不再列 D 项。

### 阶段 2：逐章审读（每章一个子代理）

按章依次执行，不并行（下一章要用上一章更新后的总名词表，待定决策编号也要连续）。每章：

1. 主代理用 Agent 工具派一个 `general-purpose` 子代理，`run_in_background: false`，提示词按 [子代理提示词模板](references/chapter-subagent-prompt.md) 填写章号、文件路径、页码范围。派单开头的“重点防范”用大白话写本书已出现过的漏检类型（如“同一方法多种叫法不能以‘描述性’为由保留”），不只写知识库编号。
2. 子代理照 chapter-checks.md 先逐段精读写出 `第NN章-名词表.md`（以脚本候选为起点，按名词类别清单逐类核查），再用它审本章，写出 `第NN章-审查记录.md` 和修订规则；会在后面章节再出现的对象并入总名词表 `名词表.md`；跨章回指、本章才正式定义而前面章节已用过别的写法等需要回到别章核对的项，记入 `回查清单.md`。交活前自己跑 `check_glossary.py` 到 0 条。只向主代理返回简短摘要。
3. 主代理收到后先跑 `check_glossary.py 第NN章-名词表.md`，不为 0 条就把未决行列表发回同一个子代理补判，再读摘要（必要时抽查记录文件），不把整章内容拉回自己的上下文。
3a. **压缩复核（固定环节）**：另派一个子代理，只读本章名词表的“放过清单”（判为“不同对象”“逐项核对”的行）、脚本候选和它们引用的段落，逐条重判，不重读全章，重判标准是 rules.md 判定原则第 2 条的读者角度，派单按派单模板“复核子代理”一节填（读者会当成一个东西的就推翻“不同对象”）；结果写 `第NN章-复核记录.md`、`第NN章-复核规则.json`。原定连续三章推翻数都在 3 条以内就撤；高阶网络第 7～15 章的推翻数是 3、8、5、9、4、7、5、9、9，没有降下来，所以不撤。
4. **章末确认**：复核交回后、修订写入副本前，把本章新增的 D 项（有倾向的待确认）和体例待定项一次发给用户（AskUserQuestion 或清单），逐条写清问题、倾向方案、另一选项、处数，等用户答复后按选择写规则再出稿（2026-11-17 用户定恢复 11-09 的做法：“每章跑完步确定的地方都找我确认一下”；11-12 的“按倾向出稿、做完一并报”作废）。结论写回 `待定决策.md` 和总名词表（状态改为“用户确认”）。牵涉其他章节的（如核心名称该用哪一个），定了再进入下一章。书名、章题核心名称的统一方向开审前先问定；审读中才发现的核心名称冲突，当场停下来问。
5. 向用户报一句进度（第几章完成，发现几处问题、几处待确认）。

### 阶段 3：回查与章间核对（审了两章及以上时，主代理或子代理）

1. 处理 `回查清单.md`：后面章节才正式定义的名称、跨章回指，定向读取相关章节核对，结论补入对应章节记录和修订规则。
2. 把各章的本章名词表并排比较：同一对象在两章写法不同的，按判定原则定统一方向，同样补入。

### 阶段 4：汇总报告（用户要求时才出，主代理）

现在交付的是修订稿（阶段 5），汇总报告不是每本书必做，用户要时再出。

1. 从各章记录汇总，生成自包含的 HTML 报告（用户指定格式优先）。
2. 结构：审查范围与稿本 → 名词表（最终版）→ 明确问题 → 待确认 → 已核查、未核查、范围外。同类问题可以合并说明，但每个位置都要能单独定位。
3. 涉及图表的问题嵌入原页截图作证据。
4. 检查报告能打开、图片清楚、定位正确后再交付。

### 阶段 5：回写（仅当用户要求改稿）

- 用 `scripts/revise_docx.py` 把各章修订规则写进副本：最小必要的字词级真实修订（tracked changes）和批注，原稿与既有修订不动；写入前用 `check_rules.py` 预检。
- 回写后按接受修订后的现文重读修改句及相邻句，检查重复、搭配和含义变化，必要时撤回不必要的修改。
- 图片、公式等不能安全编辑的对象只给定位意见，不声称已修改。

### 阶段 6：经验入库（需用户同意）

审查结束后列出值得入库的候选案例（漏检、误改、新的边界判例）。用户同意后，按主表“当前不一致的原文—对照依据原文—正确改写—原因梳理”四栏追加到主表，只维护这一份主表，不另建备份。

## 四、D 项台账（主代理）

三档的定义和门槛在 rules.md 第二节。台账只由主代理管：

- **写入前先问用户**：见阶段 2 第 4 步。
- 待定决策统一登记在工作目录的 `待定决策.md`：编号、问题、当前采用的倾向方案、另一个选项、涉及章节、状态。同一问题在后续章节沿用同一编号和同一倾向，不重复开新编号。
- 用户确认后，状态改为“用户确认”，并同步到名词表；用户选了另一个选项时，按该编号找出所有相关修订统一改换，后续章节按新方案执行。
