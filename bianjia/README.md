# bianjia（编加流程的脚本）

把每章“准备”和“合并”里不需要判断的固定命令串起来。审稿的判断仍由模型做：脚本只导出、搜索、预检、写入、核对，遇到要判断的地方停下并列清楚。

2026-11-10 建，用《高阶复杂网络系统异常检测》第 13 章验证：准备产物、合并规则、合并稿与当时手工做的逐字一致。

## 每章的完整流程（2026-11-12 起，润色在最前）

| 步 | 做什么 | 谁做 | 产物 |
|---|---|---|---|
| 1 润色 | 照润色技能 `runse` 做到第 4 步；工作目录固定是 `<书目录>/润色/第NN章/` | 润色、复查子代理各一组（Opus 5.5，high） | 润色修订稿、**润色后底稿**、正文.txt、终稿.json、复查汇总.md |
| 2 准备 | `prep_chapter.py`：自动拿润色后底稿当底稿（润色前导过的加 `--force`） | 脚本 | `source/` 下的段落文字、候选、图片 |
| 3 审 | A 一致性、B 通读（不查句子和标点）、C 查证并行；图片转写在第 1 步时就可以做 | 子代理 | 修订规则、通读发现、名词表 |
| 4 复核与待定 | 压缩复核；D 项发给编辑定 | 子代理、编辑 | 复核规则 |
| 5 合并 | `merge_chapter.py`：规则写进润色后底稿 → 体例脚本 → **补标**（把润色改动标回去）→ 核对 | 脚本 | 合并稿（唯一的一份修订稿）、合并报告、改动句复读 |
| 6 复读 | 读 `改动句复读.md`，每段都读；别扭的句子、重复批注处理掉 | 主会话 | — |
| 7 交付 | `merge_chapter.py … deliver` | 脚本 | 交付目录里的一份修订稿 |

- **一口气做完，中间不停**（2026-11-12 编辑定）：从第 1 步到第 7 步连续做，不用先把流程和派单给编辑看、等编辑说开始。只有做不下去或会弄坏东西时才停：脚本核对不过、交付目录有锁文件、交付目录里的稿编辑改过、原稿有没接受的修订、一组润色退回超过三分之一。做完一次汇报：各修订人多少处、要编辑看的疑点、D 项和体例待定项。
- 润色过没有，脚本看 `<书目录>/润色/第NN章/` 里有没有 `第NN章-润色后底稿.docx`、`正文.txt`、`终稿.json`（位置可用配置“润色目录”改，默认 `润色/第{NN}章`）。有，底稿就是润色后底稿，“原稿”指作者原稿，补标自动做；没有，照老办法在作者原稿上做，准备报告会提醒“这一章还没有润色”。
- 合并稿里有三种修订人：“Claude（润色）”“Claude”“Claude（建议）”。拒绝全部修订等于作者原稿，接受全部修订等于定稿，脚本核对过才出合并稿；没补标的那份留作 `合并/第NN章合并稿-补标前.docx`。
- 润色终稿要在第 3 步之前定下来；之后再改，第 2 步加 `--force` 重导、规则重新预检、第 5 步重跑。
- 润色留下的“留给一致性审查的名词”（`润色/第NN章/复查汇总.md`）写进 A 的派单，准备报告会提醒。
- 合并后通读不再查句子，第 6 步的复读是后两遍改动的唯一一道句子检查。

## 每本书先建配置

书的工作目录下放 `本书配置.json`（样例：`~/Claude/高阶复杂网络-一致性审查/本书配置.json`）：

| 键 | 含义 |
|---|---|
| 原稿 | 作者原稿路径，`{n}` 章号、`{NN}` 两位章号；个别章不同写进“原稿覆盖”（写的是作者原稿，不用指向润色后底稿） |
| 排版PDF、PDF页码偏移、章 | 每章的 PDF 页码范围 `"13": {"pdf": [186, 201]}` |
| 全书替换 | 本书已定的统一替换，脚本列出每处，改不改由模型判断 |
| 常搜 | 每章都要搜的写法（名词表“必搜写法”会自动带上） |
| 出稿后 | 写入修订后依次跑的体例脚本；带“参数键”的要每章给参数，没给就跳过 |
| 交付目录、交付文件名 | 放给编辑看稿的位置 |
| 合并目录、通读发现 | 默认 `通读/第{NN}章/合并`、`通读/第{NN}章/通读发现.json` |
| 润色目录 | 默认 `润色/第{NN}章`；里面有润色后底稿、正文.txt、终稿.json 时，这一章按润色过处理 |

## 每章用法

P=~/.venvs/book-review/bin/python，S=~/.claude/skills/bianjia/scripts

**准备**（润色之后、派单之前）

    $P $S/prep_chapter.py <书目录> 13 [--search 本章加搜的写法,…]

读 `source/第13章-准备报告.md`：处理“要处理”各项；判断“要你判断的替换”，用下面的命令写成机械规则：

    $P $S/mech_rules.py <书目录> 13 --add 辨别器=判别器 --add 重建=重构 [--skip P94] [--whole]

**合并**（A、B、复核都交回，D 项用户定完之后）

    $P $S/merge_chapter.py <书目录> 13            # rules + style
    $P $S/merge_chapter.py <书目录> 13 style --set 式下段开头='其中，X是|其中，Y为' --drop-comments 0,31
    $P $S/merge_chapter.py <书目录> 13 deliver    # 查锁、查用户是否改过、旧版移废纸篓、放进交付目录

停下来时按提示改这三个文件再重跑：`合并/A规则-调整.json`、`合并/通读规则.json`、`合并/通读补-手写.json`。
出稿后读 `合并/改动句复读.md`，看 `合并/合并报告.md` 里有没有重复批注。润色过的章，合并稿已经把润色改动补标回去，报告里列出各修订人的修订数和核对结果；补标或核对没过脚本会停下，不会出合并稿。

## 脚本不做的事

- 判断哪处该改、两路冲突留哪条、重复批注删哪条、改动句通不通。
- 每本书特有的操作（换新图、Word 原生图表抽数据、段首补“其中，”）：模型自己做，做完接着跑。
- 派子代理、问用户 D 项、更新名词表和交接文件。
