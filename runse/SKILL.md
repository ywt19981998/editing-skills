# 润色

目标：拿到稿子后先过一遍，把读不顺的句子改顺，让后面的一致性审查、通读和编辑自己看稿时，不再被病句和翻译腔绊住。润色只改说法，不改内容：公式、符号、数值、引注、外文原样，意思不增不减。

润色是各遍里改得最深的一遍，也最容易改坏：把公式旁的修饰关系判反、顺手换了术语、加了原文没有的解释。润色稿读起来都很顺，光看是看不出哪里改坏了的。所以流程的后一半全是核对——脚本查硬指标，另派一个没参与润色的子代理拿原文逐句对，写进 Word 之后再核一遍。**这三道哪一道都不要省。**

## 一、谁做什么

| 谁 | 做什么 | 模型 |
|---|---|---|
| 主会话 | 跑脚本、分组、派单、处理核对出的问题、交付 | — |
| 润色子代理，每组一个 | 按[润色派单](references/润色派单.md)逐段润色 | Opus 5.5，high |
| 复查子代理，每组一个 | 按[复查派单](references/复查派单.md)查润色有没有改出新问题 | Opus 5.5，high |

- 润色和复查都要用 Opus。2026-11-11 用第 14 章试过：同一份派单，Sonnet 会把公式旁的修饰关系判反，整段翻译腔也只调语序、不重写；Opus 两样都做对了。
- 复查必须另派，不能让润色的那个子代理自己查自己，也不要由主会话代劳。
- 主会话自己不润色。逐段改写很占上下文，分给子代理，主会话只看核对结果。

## 二、流程

`P=~/.venvs/book-review/bin/python`，`S=~/.claude/skills/runse/scripts`。工作目录记作 `D`，放在书的工作目录下，如 `<书目录>/润色/第14章/`。

### 0. 准备

```
$P $S/prep_polish.py 原稿.docx D --pdf 排版或导出的.pdf --pages 202-218
```

产出 `D/正文.txt`（每行一段，带段号；公式、图、脚注号用占位标出；标题、图表题、独立公式、表格带【不改】标记）、`D/页面/`（PDF 页面图片）、`D/准备报告.md`（分组建议、每组对应的页码、要看一眼的标记）。

- **PDF 是给子代理看公式用的。** 公式在 Word 里是对象，导出的文字里只有占位；不知道占位是什么公式，公式旁边的话就容易改错。有排版 PDF 就用排版 PDF（书的 `本书配置.json` 里有路径和每章页码）；没有就请编辑在 WPS 里“输出为 PDF”。稿子里没有公式时不需要 PDF。
- **原稿里有没接受的修订**时脚本会停下。润色要在干净的稿子上做，先问编辑这些修订怎么处理。
- **一个文件装两章**：加 `--from '^第\s*3\s*章'`（从这一段起）或 `--to '^第\s*3\s*章'`（到这一段之前）。“参考文献”以后的内容不导出。
- 读一遍 `准备报告.md` 里“标记要看一眼的”，再扫一眼 `正文.txt`：正文段被标成标题，这一段就润色不到；标题被当成正文，问题不大。标错了加 `--body 段号` 或 `--skip 段号` 重跑。
- 分组照报告的建议（每组不超过约 4500 字、30 个正文段，在节的边界上切）。组再大，后半部分容易草草带过。
- 本书已有名词表时，把“采用写法”抄成一行一个的 `D/术语表.txt`，后面核对时用；没有就不用。

### 1. 润色

每组派一个子代理（general-purpose，Opus 5.5，high），各组在同一条消息里一起派，每个大约两三分钟。派单原文：

```
请完整读取并严格按这份派单执行：~/.claude/skills/runse/references/润色派单.md
- 正文：D/正文.txt
- 你负责的范围：S038～S078
- 页面：D/页面/ 里的 p205.png～p209.png（排版稿是旧一版，文字和正文略有出入）
- 这本书：《书名》，学术专著，读者是本领域的研究生和科研人员
- 本书体例：式下说明用“其中，”引出
- 结果写到：D/结果-2.json
```

- 页面范围取准备报告里这一组的页码，前后各放宽一页（页码是按文字对出来的，独立公式可能落在下一页）。报告说页码对不上的，把整章页面都给它。没有 PDF 就写“页面：无”。
- “本书体例”只抄 `体例.md` 里跟句子和标点有关的几条（式下说明的引出语、括号和列举的用法）。数值、单位、空格、编号的写法不归润色，不要抄进去；没有体例表就写“无”。
- 派单里故意没有“不许换名词”的硬规定（2026-11-11 编辑定）：写了，子代理连该重写的直译句也不敢动。名词有没有被换，放到复查去查，换了的一律恢复原词——哪怕原词是译错的（2026-11-12 编辑定：误译的术语留给一致性审查在全书范围内改）。

### 2. 机器核对

```
$P $S/check_polish.py 原稿.docx D/正文.txt D D/结果-*.json [--terms D/术语表.txt]
```

产出 `D/核对单.md`、`D/对照.md`（给复查看）、`D/对照.html`（红绿标色，给人看）。

- **硬问题**（占位、数值、引注序号、外文有增减，漏段，不能拆的文字块被改）要先清掉，退出码是 0 才往下走。把核对单里这几条发回原来那个子代理改（用 SendMessage 续派，它还记得上下文）；只有一两处的，主会话对着原文改 `结果-*.json` 也行。改不好的段，把它的 `changed` 改成 `false`（这一段不润色）。
- “给复查的线索”不用主会话处理，它们已经写进 `对照.md`。其中“书面语换成了口语”“一词换一词”两类（2026-11-12 编辑定：学术著作一律用书面语，可换可不换的词不换）由复查逐个恢复；终稿的核对单里“书面语换成了口语”还剩不少的，说明复查没管，发回复查子代理补。
- 只润色一部分时加 `--range S038-S078`（下面第二遍核对也要加），否则范围外的段会被报成漏段。

### 3. 复查

每组另派一个子代理（general-purpose，Opus 5.5，high），一起派。派单原文：

```
请完整读取并严格按这份派单执行：~/.claude/skills/runse/references/复查派单.md
- 对照：D/对照.md
- 你负责的范围：S038～S078
- 页面：D/页面/ 里的 p205.png～p209.png
- 结果写到：D/复查-2.json
```

都交回后合并，再核对一遍终稿：

```
$P $S/apply_review.py D/正文.txt D/终稿.json --polish D/结果-*.json --review D/复查-*.json
$P $S/check_polish.py 原稿.docx D/正文.txt D D/终稿.json --prefix 终稿- [--terms D/术语表.txt]
```

- `apply_review.py` 把复查给的修正逐条替换进润色稿，整段退回的恢复原文，写出 `终稿.json` 和 `复查汇总.md`。有修正没对上（复查抄的原话在润色稿里找不到，或不止一处）会列出来：改复查文件里那一条的 `old`，或者发回复查子代理重写，再跑。
- 第二遍核对退出码必须是 0。复查的修正也可能碰掉数值或占位，所以要再核。
- 读 `复查汇总.md`：复查修了什么、退回了哪些段、哪些要编辑自己看。再抽两三段打开 `复查-*.json` 看 `words`：`对照.md` 里脚本提示“名词消失／新出现”的词，复查有没有逐个交代。一组改了十几段，`words` 全是空的、一处没修，多半是没认真对，重派。如果一组里退回或修正的段超过三分之一，说明这组润色整体有问题，先把情况告诉编辑，不要直接交付。

### 4. 写回 Word

```
$P $S/polish_to_docx.py [--terms D/术语表.txt] 原稿.docx D/正文.txt D/第14章-润色修订稿.docx D/终稿.json
$P $S/verify_polish_docx.py 原稿.docx D/第14章-润色修订稿.docx D/正文.txt D/终稿.json
$P $S/accept_polish.py D/第14章-润色修订稿.docx D/第14章-润色后底稿.docx D/正文.txt D/终稿.json
```

- 写回只改公式、图、脚注号、域之间的文字，这些对象本身不动；修订按词切，不会把一个词拆成半个；只增删空格的改动不写。修订人是“Claude（润色）”，编辑在 WPS 里可以按修订人筛出这一遍的改动。
- 核对脚本最后一行是“问题：无”才算写对：接受全部修订等于终稿，拒绝全部修订等于原稿，公式和域一个不少、没有落进修订里，没改的段落原样。两个脚本取文字用的是两套代码，对得上才可信。
- 写回脚本说“域里的文字被改了”“落在域的显示文字中间”的，是交叉引用或文献序号旁边的字动了，打开稿子看一眼那一处。
- 第三条命令生成**润色后底稿**：把润色修订全部接受后的干净稿，逐段核对等于终稿才写文件。它是给后面的一致性审查和通读当底稿用的中间文件，不交给编辑。
- 有哪一段写不回去，脚本整份都不写并列出这些段：在 `终稿.json` 里把它们改好或退回原文，从第二遍核对起重跑。

### 5. 交付

告诉编辑：

- 修订稿在哪；改了多少段、多少处修订；`对照.html` 可以在浏览器里看红绿对照。
- 复查修掉、退回了什么（照 `复查汇总.md` 说几条有代表性的）。
- `复查汇总.md` 里“留给一致性审查的名词”一节（润色想改、复查已恢复原词的，如误译的术语）：原样交给编辑，并交到一致性审查手里，否则润色看出来的误译就丢了。
- 要编辑自己看的：复查标了 `ask` 的、润色时“读不懂”没改的。
- 没覆盖的：公式和图里的内容、表格、标题、参考文献；错别字、数字单位、术语统一不是这一遍的事。

往编辑看稿的文件夹里放文件之前，先查有没有锁文件（`.~*`、`~$*`，说明编辑正开着）；要覆盖旧版时，旧版移到废纸篓，不要直接删。编辑已经开始在修订稿上改了之后，再发现的问题只列位置和改法，不重新生成。

## 三、和后面几遍的关系

润色在最前面。后面的一致性审查和通读都用**润色后底稿**当底稿：它们要找的原文，在润色时可能已经改掉了，拿作者原稿去审会对不上。

- 用 bianjia 脚本的书：在 `本书配置.json` 的“原稿覆盖”里把这一章指向润色后底稿，再跑每章准备（已有旧的导出文件时加 `--force`）。
- `复查汇总.md` 里“留给一致性审查的名词”交给一致性子代理当线索。
- 通读不再查句子和标点（2026-11-12 编辑定），这两样只有润色这一遍管。稿子不润色就直接通读的，要告诉编辑句子和标点没人查。
- **合成一份修订稿的办法还没做好**（2026-11-12）：后两遍的修订是写在润色后底稿上的，把润色改动补标回去的脚本还没有。在它做好之前，一章会有两份稿——润色修订稿（对作者原稿）和一致性加通读的修订稿（对润色后底稿）。交付前先问编辑怎么给，不要自己定。

## 四、经验入库

编辑看润色修订稿时指出的问题，按类型补进派单，写成不带本书内容的一般说法，例子另举：

- 改坏了的（意思变了、名词被换、加了内容）：补进[复查派单](references/复查派单.md)“逐段查这六件事”里对应的一条。
- 该改没改的句式：补进[润色派单](references/润色派单.md)“要求”第 1、2 条的列举或例子。
- 标点、引出语一类的体例：写进本书 `体例.md`，下次派单时抄进“本书体例”。
